A block builder in a trust domain, with far less inside it.

A builder in a TEE asks whoever sends it transactions to trust what is inside the TEE. Where builders have said what that is, it is a Linux image: a kernel, an init system, a C library, a TLS library, an execution client and the builder. This one is a single program of 4.2 MB, written in Lean, with nothing else above the firmware. It runs in an Intel TDX trust domain on Google Cloud, bids at four relays in every slot, and a block it built there is on mainnet.

The claim, and how narrow it is

Less inside. Not yet "less to trust".

The claim is about what sits inside the trust domain and can therefore read a transaction there: one program of this size and kind, and not a Linux image. The network card's driver, Ethernet, IP, TCP, DNS, TLS 1.3, X.509, HTTP, the EVM, the Merkle-Patricia trie, BLS signing and the builder itself are all Lean in that one program. Lean is a language in which a program cannot reach memory it was not given. That is all "Lean" means here: it does not mean proved, and nothing proved covers the builder.

It is not a claim that somebody who sends this builder a sealed transaction has less to trust in all. The machine that feeds the guest is outside it, measured by nobody, and chooses every other transaction of every block. What it can learn about a sealed transaction that way has not been tested by anyone. Until someone other than us has tried, read "less inside", and not "less to trust".

How it works

The node stays outside. That is what lets the inside be small.

A builder normally carries a whole execution client and the chain's state. This one holds no state. Each round it is handed transactions together with proofs of the state they touch, checks the proofs, and builds on that.

1 · outside, ours, unmeasured

The feeder

An ordinary machine with an ordinary node. About three times a second it sends the guest the transactions pending in public and proofs of the state they read. It sees the public flow and chooses what the guest sees of it.

2 · inside the trust domain

The guest

Checks the proofs, orders the transactions by what they pay, runs them, and signs a bid for the block with a key it drew when it started and that never leaves it. Then it posts the block to the relays itself, over its own TLS.

3 · outside, as for any builder

Four relays

Flashbots, Ultrasound, Aestus and Titan. Each sees every block whole, as it does from any builder, and publishes every bid beside the key that signed it.

4 · outside

The proposer

Takes the best bid a relay offers it. Ours is taken when it pays most, which, from the public pool alone, it does not.

Private flow has to be sealed to the guest, so that the feeder carries it without reading it. Anybody can do that through a door that hands the guest a sealed transaction and nothing else. Nobody outside this project has yet.

It won because it was paid for. The project's owner told the feeder to add 0.01 ETH to the bids of five slots, and the first of the five was taken. The payment is the block's first transaction. It was signed outside the guest, by the feeder, with a test wallet's key: the guest signs no payment and does not know one from any other transaction. Without it the block was worth 0.00176 ETH, and the best other bid Titan lists for that slot was 0.00422 ETH.

What it shows: a block built in that guest, on that cloud, is one that relays pass on and a proposer signs, and it is valid on the chain. What it does not show: that such a block wins unpaid. No sealed transaction was in it.

Three earlier blocks (26463293, 26465583 and 26470277, 21 and 22 November) were built by earlier images on a machine of the project's own, each paid for with 0.02 ETH. Two of them hold a transaction that was sealed to the guest and that the feeder carried without seeing. In both the sender and the feeder were the same program on the same machine, so they show that the parts fit, and nothing about an adversary.

The summed figure is the truer one: the slots that pay are far above the median, and in those ours is furthest behind. The reason is what it sees. A winning block is mostly transactions sent to builders in private, and this builder has only the public pool.

When the bids are made. The taken bids that relays give a time for reached their relay about a second after the slot began. Ours stopped about a second before the slot until 27 November, then went on to 0.6 s after it, and since 02:58 UTC on the 28th to 0.9 s after. Inside each slot, the last block of the later rule against the last one the first rule would have sent: 12% more at 0.6 s, and 15% more at 0.9 s over ten hours. The later rule cost 26 refusals for lateness in those ten hours, and no slot went without a bid for it.

Trust

Who you are still trusting

  1. Intel: the processor, the TDX module, the quoting enclave. The processor's random numbers are the only source the keys are drawn from.
  2. Google's firmware. It starts the guest, stays in its address space, and could read its keys. It is measured, and Google signs for the measurement, which is checked. What it does is Google's word: nobody else builds it.
  3. The image, whose measurement anyone can work out from the file.
  4. Four certificate roots the image holds for the relays' names.
  5. What built the image: Lean's compiler, the C compiler and linker that come with it, and the ready-made modules it links against.

Not trusted with a transaction's bytes: Google as host (but for its firmware), the cloud's network, and the feeder. What they can still do is said at length in the threat model. In short: any of them can starve the guest, and the feeder chooses the rest of every block.

What this is not. It is not a competitive builder: it sees only the public pool, and the one block proposers have taken from Google Cloud was paid for. It guards nothing private yet: the running instance holds a key for signing bids, which guards no money, and no stranger has sent it a sealed transaction. It is not the same shape as a builder with its node inside: one machine outside chooses every other transaction of the block, and what it can find out about a sealed one by doing so is unmeasured. Sealing hides a transaction's bytes from that machine, not what the transaction does. It is not fast: one core, one block at a time, a third of a second a round. And it is not old or reviewed: the first commit is of 16 November 2026, and nobody outside the project has read any of it.
Check it yourself

From a bid at a relay back to the source

A relay lists every bid it is sent beside the key that signed it. The guest says, in a TDX quote, that the key is its own. So a bid can be followed back to source with nothing from us but the repository.

  1. The bid. Ask a relay for the bids under the builder's key. live/builder.txt has the key and a link.
  2. The key is the guest's. This page checks the quote in your browser, with nothing sent anywhere, as far as a page can: it takes the image's measurement from a file of ours.
  3. The guest is this program, on Google's firmware. Build the image from the commit live/builder.txt names and run scripts/gce-check on it. It asks whether the quote's signatures lead to Intel's root, whether Intel calls the platform up to date today, whether the measurement in the quote is what Google's firmware measures for that file, whether Google signed for the firmware, and whether the quote is of that key.
  4. The program is this source. Built from nothing on a machine of GitHub's, the image is the same file byte for byte, and the quote passes against the file built there. The runs are public.

Every key the builder has bid under on Google Cloud, eleven so far, is in the report, with the first and last slot bid under each.

Build it

Linux on x86-64 and Lean through elan. The image comes out the same file each time.

git clone https://github.com/posix4e/cluck && cd cluck/evm
# fetch mathlib's ready-made modules first: the command is in evm/README.md
lake build
scripts/build-efi tdx                 # .lake/build/efi/tdx/evm-os/BOOTX64.EFI

Starting it on a TDX machine of your own or on Google Cloud, checking a quote against the file, and feeding it from a node are each a few commands, under "Reproduce it" in the report.
