A transaction only the builder can read.

The block builder in the trust domain holds a key that never leaves it. This page checks that key against the machine's own quote, seals your signed transaction to it in your browser, and hands the sealed bytes in. Nobody between you and the builder's program can read them: not this site, not the door that carries them, not the people who run the machines.

Looking for the builder…
First

The builder's key, and whose it is

The key is asked for with 32 random bytes made here, so the quote that comes back with it cannot be an old one. Nothing is sealed to the key unless every line below holds.

Then

Your transaction

What a wallet or cast mktx gives as the raw transaction: signed, and not sent anywhere yet. It is a real transaction on mainnet. If it lands, it has happened.

After that

What happens to it

  • The builder tries it in every block it builds until the time you chose runs out, then drops it. The time is sealed in with the transaction, so nobody who carries it can have it built in later.
  • It lands only if one of this builder's blocks is the one a proposer takes, and that is rare. The builder sees the public pool and nothing else, and its blocks have been worth a third or less of the ones that win. What your transaction pays the block's builder counts towards its bid; a tip large enough to make the difference changes the odds, and nothing else here does.
  • Nothing tells you here whether it went in. Watch the transaction's sender on a block explorer.
  • If you also send it elsewhere, whichever lands first uses up its number, and the other can no longer happen.
What this does and does not keep from others

Read this before sending anything that matters

  • Its length shows. The sealed bytes are as long as the transaction, and whoever carries them sees that, when you sent them, and from what address.
  • Which accounts it touches becomes known to the machine that feeds the builder. The builder holds no state of the chain. For a transaction sealed as this page seals it, it asks its feeder for proofs of the accounts and storage the transaction reads, and so the feeder learns which those are. A command in the repository (evm/scripts/seal-with-proofs) seals the proofs in with it, and then nobody is asked.
  • Whoever feeds the builder can find out what it does, without reading it. The feeder chooses the other transactions of the block and may write them: one put before yours sets the state yours runs in, one put after reads what yours changed, and the relays publish each bid's gas and value. A few such blocks can show which contract it touched and which way it moved a price. What stays hidden until the block is in the chain is the transaction itself: its bytes, its sender, its signature. The feeder is this project's machine; this is what it could do, not what it does.
  • The relays see the block, as with every builder, and publish what each bid paid.
  • The door can lose it. It can drop what you hand in or hold it back until its time has run out. It cannot open it or change it.
  • That the key belongs to the published program rests on a record of ours until you check that too: the other page says how, with one command, and a machine of GitHub's does it whenever the record changes.
  • The firmware under the program is Google's, and could read what the program reads. The report says what else is trusted.
